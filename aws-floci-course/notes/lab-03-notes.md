# Lab 03 notes

## Review Q2 (draft): policy for a bucket that does not exist
An IAM policy is a statement about ARNs, not a reference to existing objects, so granting
access to arn:aws:s3:::usms-student-data before the bucket exists is valid. The permission
has no effect until something appears at that ARN. When the bucket is created, usms-web-01
gains the ability to write transcripts through its instance profile, with no access key on disk.

## Review Q1: what Step 8 consumed, and what a fault in each would have done

| Input | Source | If wrong or missing | Failure type |
|---|---|---|---|
| Subnet (`subnet-d0e2e873`) | Lab 2 | A nonexistent ID gives `InvalidSubnetID.NotFound`. A *wrong but valid* subnet (e.g. the private one) launches fine, but the instance gets no public address and no route to the IGW. | Immediate if missing; **silent** if merely wrong |
| Security group (`usms-app-sg`) | Lab 2 | A nonexistent ID gives `InvalidGroup.NotFound`. Omitting it attaches the VPC's default group, which launches fine but admits the wrong traffic. | Immediate if missing; **silent** if omitted |
| Instance profile (`usms-ec2-app-profile`) | Lab 1 | A nonexistent name is rejected at launch. Omitting it launches fine, but the instance has no AWS identity, so S3 calls in Lab 4 fail later with no credentials. | Immediate if misnamed; **silent** if omitted |
| Key pair (`usms-app-key`) | Lab 3 | A nonexistent name gives `InvalidKeyPair.NotFound`. | Immediate |
| User data (`user-data.sh`) | Lab 3 | A syntax error is accepted by the API and fails inside the guest at boot. On this Floci build the script ran but the metadata calls returned empty values and `systemctl` failed, so the page was served blank and nothing listened on :80. | **Silent**, and the hardest to debug |

The pattern is that the IDs and names the API can check fail immediately, while anything that is a *valid choice of the wrong thing*, or the *content* of a script, fails silently. This is why the lab reads configuration back after the launch instead of trusting that run-instances returned an ID.

## Review Q3: why putting deployment in user data does not redeploy on restart

User data is executed by cloud-init at first boot only. Stopping and starting an instance, or
rebooting it, does not run the script again: the instance keeps its root volume, and cloud-init
records that this instance has already completed its first boot. So a colleague who edits the
user data and restarts the instance would find nothing changed. Editing user data also requires
the instance to be stopped, and the new content is simply ignored on the next boot unless
cloud-init is told to treat it as a fresh instance. The idea therefore confuses "configure at
creation" with "deploy on every start".

Two approaches that do work:

1. **Replace the instance instead of restarting it.** Put the new version in user data (or, better,
   in a new AMI or launch template version) and launch fresh instances, then retire the old ones.
   Every new instance runs first boot, so it picks up the new deployment. This is the immutable
   infrastructure approach, and it is how an Auto Scaling group in Lab 6 does rolling updates.
2. **Make the script run on every boot, or pull deployments separately.** Either mark the user data
   as a per-boot script with a cloud-init directive (for example placing it in the per-boot scripts
   mechanism), or have the user data install a small service or systemd unit that fetches the
   latest release from S3 or a repository when it starts. A deployment tool such as CodeDeploy or
   AWS Systems Manager Run Command can also push a release to running instances without any
   restart.

Observation from this lab: on Floci the user data did execute, but only once, at launch. After the
Step 18 stop/start and the Step 19 recovery, the bootstrap log was not regenerated by a re-run of
the script, which is consistent with the first-boot-only behaviour. (Floci runs the script itself
rather than through cloud-init, so this part is only partly comparable to real AWS.)

## Review Q4: auto-assigned public address vs Elastic IP

| Dimension | Auto-assigned public IPv4 | Elastic IP |
|---|---|---|
| Who owns it | AWS. It is borrowed from a pool for as long as the instance runs. | Your account. It is a resource with its own allocation ID, independent of any instance. |
| When it changes | Released on stop and a different one is assigned on start. It also cannot be kept if the instance is terminated. | Never changes until you release it. It survives stop/start and can be moved to another instance. |
| What it costs | Charged as a public IPv4 address while in use, with no separate lifecycle to manage. | Same hourly public IPv4 charge, and it is also charged while allocated but not associated with a running instance, which is the common surprise on a first bill. |
| On instance stop | Released. The instance has no public address while stopped. | Stays allocated to you and re-attaches on start. |

Failover procedure only possible because of the difference: if usms-web-01 fails, launch a
replacement (or use usms-web-02), then call associate-address for the same allocation ID with
the replacement instance ID and --allow-reassociation. The public address that DNS and clients
already use moves to the healthy instance in seconds, with no DNS change and no waiting for TTLs
to expire. An auto-assigned address cannot be moved, so the replacement would get a new address
and every DNS record would have to be updated.

Observation from this lab: in Step 18 the Elastic IP association (eipassoc-08c2a5ef1a0657b43)
stayed bound to usms-web-01 across stop/start, and again after the Floci restart in Step 19.
Floci did not show the auto-assigned address being released (the instance reported 127.0.0.1
throughout), so that half of the comparison is conceptual, not observed.

## Review Q5: where an EBS volume and a snapshot are stored, and what that means for AZ failure

An EBS volume lives inside one Availability Zone's storage fabric. It is replicated within that
AZ, but it cannot be attached to an instance in a different AZ, because the instance and the volume
must be reachable over the same AZ-local storage network. A snapshot is different: it is stored
in S3-managed storage that spans the whole region, so it is not tied to any single AZ. That is
why a snapshot can be restored as a new volume in any AZ of the region, while the original volume
cannot be moved.

Implications for designing a system that must survive the loss of one AZ:
- A volume alone is not durable against an AZ outage. If the AZ goes down, the volume and its data
  are unreachable until the AZ recovers.
- Data that matters must exist outside the volume's AZ: take regular snapshots (which land in the
  region), or replicate at the application layer (for example a database standby in the other AZ).
- Recovery from an AZ loss means creating a new volume from the latest snapshot in a surviving AZ
  and attaching it to an instance there. Anything written after the last snapshot is lost, so the
  snapshot frequency sets the recovery point.
- The compute tier should already span AZs, as usms-web-01 (us-east-1a) and usms-web-02
  (us-east-1b) do, so a surviving instance exists to receive the restored volume.

Observation from this lab: usms-web-data-vol was created in us-east-1a, the same AZ as usms-web-01,
derived from the instance rather than typed. Floci returned UnsupportedOperation for attach-volume
(both the real attach and the cross-AZ test), so the ZoneMismatch error was not observed. Real AWS
would reject the cross-AZ attach with InvalidVolume.ZoneMismatch. This answer is conceptual, not
observed.

## Review Q6: is verifying six configuration properties an adequate substitute for a live request?

It is a useful but incomplete substitute. The six checks (instance running, subnet route to an
internet gateway, gateway attached, security group admitting tcp/80, a public address present,
NACL allowing traffic) cover every link that AWS itself controls on the path from a browser to
the instance. They are cheap, they run without sending traffic, and they localise a fault: when
a real request fails, the first failing check names the broken link. They also catch the common
mistakes (missing route, detached gateway, closed port) before anyone has to debug a timeout.

They are not adequate on their own, because they read configuration, not behaviour. A check
confirms that a rule exists, not that traffic actually flows through it.

This lab is a direct demonstration. All six checks passed for usms-web-01, yet a request to it
could not succeed: inside the instance, nothing was listening on port 80. The user-data script
ran, but its metadata calls returned empty values and `systemctl enable --now nginx` failed
because the container had no systemd, so nginx never started. Every AWS-side property was correct
and the service was still down.

The specific class of fault the checks cannot detect is a fault inside the guest: the process
that should answer on the port is not running, is listening on the wrong port or interface, has
crashed, or is misconfigured. The same blind spot covers an application returning errors, a
host firewall (such as iptables) inside the instance, a full disk, and failures that only appear
under real traffic. On real AWS this is the one link that is not an AWS problem, and it is why
the full diagnosis needs a live probe (curl, a load balancer health check, or instance status
checks plus application logs) in addition to configuration checks.

Two caveats from this build: check 5 passed with 127.0.0.1, which is Floci's port mapping and not
a real public address, so even that "pass" was weaker than it looks; and the 127.0.0.1 request
returned a sign-in redirect from an unrelated local service, not from usms-web-01, so it was
correctly not counted as evidence.

## Review Q7: differences between usms-web-01 and usms-db-01

Identical on both: instance type (t3.micro), base AMI, key pair (usms-app-key), VPC (usms-vpc),
Availability Zone (us-east-1a), and the VPC-wide settings (10.0.0.0/16, DNS hostnames enabled).

| Difference | web-01 | db-01 | Property of |
|---|---|---|---|
| Name, Tier and Lab tags | Tier=web | Tier=data | Instance |
| Security group | usms-app-sg (80/443/22 from the internet) | usms-db-sg (5432 from the app tier only) | Instance (the group is attached to its network interface; the group itself is a VPC-scoped object) |
| Instance profile | usms-ec2-app-profile | none | Instance |
| User data | user-data.sh (installs nginx) | none | Instance |
| Elastic IP | usms-web-eip associated | none | Instance (an association made after launch) |
| Which subnet | usms-public-subnet-a, 10.0.1.0/24 | usms-private-subnet-a, 10.0.3.0/24 | Placement chosen at launch; everything below follows from it |
| Private address range | from 10.0.1.0/24 | from 10.0.3.0/24 | Subnet (the CIDR) |
| Auto-assigned public IP | yes | no | Subnet (MapPublicIpOnLaunch is True on the public subnet and False on the private one) |
| Route table | usms-public-rt: 0.0.0.0/0 to usms-igw | usms-private-rt: 0.0.0.0/0 to the NAT gateway | Subnet (association) |
| Network ACL | default ACL | usms-private-nacl | Subnet (association) |
| Reachable from the internet | yes, in principle | no, even if its security group were opened | Combination: the subnet's route, plus the internet gateway (VPC level), plus the instance's security group |

Key point: only the first five rows are choices made on the instance itself. Public reachability
is not a setting on the instance at all. It comes from the subnet it is placed in (route table,
public-IP mapping, NACL) and from the VPC's internet gateway.

Observed vs conceptual: in Floci both instances reported 127.0.0.1 as their public address (Docker's
port mapping) and Docker 172.20.0.x private addresses, so the public/private address difference was
not visible in describe-instances. What was observed is the configuration behind it: the subnets'
MapPublicIpOnLaunch values (True and False), the route table targets (internet gateway vs NAT
gateway), and the security group assignments. The resulting addresses are conceptual.
