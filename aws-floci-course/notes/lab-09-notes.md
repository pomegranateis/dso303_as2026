## Exercise notes
Ex 1 two sentences: usms-bastion-sg's egress differs in kind, because a jump host exists to INITIATE connections (SSH out to the hosts it administers) where every other tier only answers; its destination should be tcp/22 to usms-app-sg (a group reference, so it follows the web tier) plus DNS to 10.0.0.2, and nothing else. 169.254.169.254 needs no rule because link-local traffic to the instance metadata service is answered by the hypervisor/Nitro card and never passes through a security group - which is why IMDS has its own controls (Step 11).
Ex 2: both conditions sit in one Condition block, and IAM ANDs the keys of a Condition block (values within one key are ORed), so the role needs MFA AND the external ID. MaxSessionDuration 3600 is IAM's minimum (3599 rejected). sts:ExternalId is normally a cross-account control against the confused deputy; here it is a second factor that must be read off the break-glass procedure, not remembered.

## Exercise 5 part 5
The draft bucket policy's Deny (everyone but the five roles and the account root) is a resource policy on the bucket, so it is evaluated for every request to the bucket, whichever account the caller is in. USMSStudentDataReadOnly's explicit Deny is an identity policy, so it can only stop the actions of usms-transcripts-reader-role, the one principal it is attached to. A principal in another account is never governed by an identity policy in this account, but it is always governed by the bucket policy - which is why the resource policy is the control that closes the bucket, and the identity policy is the control that narrows one role.

## Review questions (Section 14)

1. Five unchanged verification scripts are a strong result because they were written before this lab, by other labs, to test what those labs built - they are independent witnesses that the security changes removed nothing functional. A plausible break: Step 15's tcp/443-only egress on usms-db-sg would break a Lab 03 check if one tested that the database can install packages over HTTP (port 80) or resolve names (port 53 - which the lab itself says it left out); and replacing usms-ecs-task-role's trust with a condition on a key ECS did not send would break every task's first AWS call. Had a script changed, I would have read the diff to find which check moved, decided whether the check or my change was wrong, and either added the narrow rule the workload genuinely needs (as Exercise 1 does for DNS) or put the old rule back from the undo document - never edited the old verifier to make it pass.

2. Attached as an ordinary managed policy, USMSPermissionsBoundary stops being a ceiling and becomes a grant. Upward: the role gains everything the boundary allows that USMSDeployBase did not - ecs:*, elasticloadbalancing:*, logs:*, cloudwatch:*, s3:Get*/List*/PutObject, iam:PassRole on "*" (no condition), iam:Get*/List*, ec2:CreateTags. Downward: nothing is capped any more, because the role now has no boundary slot filled; the boundary's Deny statements still apply as identity-policy Denies, so the iam:Create*/Attach* and network deletes stay denied. It becomes dangerous as soon as anything grants this role more (another policy attached, a new version of USMSDeployBase) - with no boundary, nothing caps it - and immediately for iam:PassRole on "*", the escalation path of Step 8. Section 8's "the boundary is attached to NOTHING as an ordinary policy" check (AttachmentCount = 0) catches it; "usms-deploy-role HAS a permissions boundary" would catch the missing boundary on real AWS.

3. Every ingress rule correct, still a breach: a dependency in the enrolment container is compromised (a malicious package update), and code running inside a task reads transcripts with the task role's own credentials and posts them to an attacker's server. Nothing came IN; the data went OUT on a connection the task opened. Steps 13-15 narrow it: the enrolment tasks can now only open tcp/443, so exfiltration over SSH, raw TCP, DNS to arbitrary resolvers, SMTP or a database protocol is gone - but tcp/443 to 0.0.0.0/0 (needed for the image pull and logs) still lets an HTTPS POST to any host through, so it narrows the channel, it does not close it. What would prevent it: egress filtering by hostname (AWS Network Firewall or an egress proxy allowing only ECR, Logs and S3 names) plus VPC endpoints for those services so the task needs no internet route at all, and an S3 bucket policy restricted to the VPC endpoint. This course cannot build it because Floci models neither Network Firewall nor interface endpoints, and security groups carry no traffic here to filter.

4. usms-ecs-task-role and usms-transcripts-reader-role trust only ecs-tasks.amazonaws.com, with aws:SourceAccount and aws:SourceArn conditions: an attacker calling sts:AssumeRole from their own machine is not that service principal, so the trust policy never matches and the call is denied whatever credentials they hold; even ECS acting for another account is refused by the conditions. They differ only in what a successful assumption would give (read-write versus read-only). usms-deploy-role trusts the AWS principal user/usms-admin-01: an attacker who has stolen that user's credentials CAN assume it from anywhere - the trust policy is satisfied - and gets USMSDeployBase capped by the boundary: deploy actions and PassRole of three roles to ECS, never identity changes or network deletion. The answers differ because a service principal can only be assumed by the service itself, while a user principal is as strong as that user's credentials - which is why the break-glass role of Exercise 2 adds MFA and an external ID on top.

5. Five controls are not five times one because they are not equally likely to fail, nor independent in every failure mode. Several share one cause: a single mistaken change to the route table (control 3) and to auto-assign (control 2) could both be made by one person in one console session, and the NACL (control 5) and the SG (control 4) are both edited through the same EC2 API with the same permissions. What defence in depth buys is that an accident in ONE place does not expose the database; it does not protect against an administrator who changes all of them. usms-enrolment-sg looks weaker in the matrix because it has one group-referenced ingress rule, but the matrix models security groups only: the tasks also sit in a private subnet with no internet gateway route, have no public addresses, and are behind the same private NACL - so they have the same network-level controls as usms-db-01; the tool simply cannot see them. "A tool that models one axis understates the defences on the other."

6. Deactivate-before-delete (step 3) protects against an unknown consumer: if some forgotten script, CI job or colleague's laptop still uses the old key, it fails while the key can still be re-activated in seconds, instead of failing permanently after deletion. It prevents the incident "the nightly transcript export silently broke and the key it needed no longer exists". Create-before-update (steps 1 and 2) protects availability during the rotation itself: there is never a moment with no valid key, which prevents an outage of the service being rotated. A long-lived key is a compromise because it is a bearer secret valid until someone remembers to rotate it - it can be copied into a repository, a log or a screenshot and used from anywhere without MFA. A real system gives humans IAM Identity Center (federated, short-lived, MFA-backed sessions) and workloads roles (instance profiles, task roles, IRSA or EKS Pod Identity), so there are no access keys to rotate at all.

7. Reading is not an adequate substitute for testing, and testing is not a substitute for reading. Reading catches what a test never exercises: in this lab it found that USMSStudentDataReadWrite also grants s3:DeleteObject to three roles, and that the auditors group's ReadOnlyAccess includes s3:Get* on every bucket - no functional test would fail because of either. Testing catches what reading misses: the lab's own allow-all query looked right on the page and returned 0 for a group that still had an allow-all rule; only running it against a known positive (usms-app-sg) showed it could never fail, and the simulator showed that create-role --permissions-boundary was silently dropped. For student transcripts I would want reading first - a complete list of who can read and write, from the documents - because the most damaging failure is an over-broad grant that every test passes, and then tests, including negative ones, that each control can actually say no.
